# RepHub 需求草案

更新日期：2026-10-11
状态：核心流程已确认，已进入 Swift 原生开发并建立首轮读取工作台。下文是完整目标，不能视为全部已实现；当前交付范围见 [README](../README.md)。

## 1. 产品定位与使用场景

面向个人 macOS 用户的代码管理客户端。在一个应用中管理 SVN、Git 及关联工作目录，并通过可配置的 AI 场景辅助代码审查和提交说明生成。

用户当前的主要问题：查看 SVN 历史、更新或检出代码需要使用 SVN 客户端，处理 Git 又需要切换到另一客户端。部分代码目录同时使用 SVN 和 Git，日常通常保持两边同步。

第一版必须覆盖的工作流程：

> 导入已有目录／克隆／检出 → 拉取或更新 → 查看变更 → AI 审查／生成提交说明 → 提交代码。

Windows 和团队共享服务不属于当前目标。

## 2. 用户已确认的需求

### 2.1 版本控制与仓库识别

- 支持 SVN 和 Git，底层版本控制能力可以扩展到其他版本控制系统。
- 支持老旧 SVN 服务。用户怀疑服务仅支持 TLS 1.0，实际协议、证书和认证兼容要求需要连接验证。
- 能识别现有本地仓库及其版本控制类型。
- 一个项目可以关联 SVN 和 Git，并查看和监控两边的情况。
- 支持拉取／更新代码、查看提交历史与变更、提交代码。
- 必须设立独立的版本控制抽象模块，下接 Git、SVN 和未来工具的具体适配器。界面和业务流程只依赖抽象契约，不直接执行工具命令或解析输出。
- 抽象层统一仓库绑定、状态、差异、历史、操作结果模型，同时保留工具专属能力，不把 SVN 强制模拟成 Git。
- 未受管理目录初始化只能选择一种管理方式；已有 Git + SVN 共管目录仍可识别，并按目标执行操作。

### 2.2 提交目标选择

- 提交界面提供 SVN、Git 目标选择，选项根据项目实际识别出的绑定提供。
- 只勾选 SVN：仅执行 SVN 提交。
- 只勾选 Git：仅执行 Git 提交。
- 同时勾选 SVN、Git：执行两边的提交。
- 用户选择的是提交目标；Git 提交之后是否同时推送远端，尚未确定。

### 2.3 可配置 AI 场景

- 用户可以创建不同功能场景，配置各自的提示词。
- 至少提供代码审查、提交说明生成两类场景。
- 代码审查能够检查选定的代码改动。
- 提交说明生成能够按照用户配置的提示词生成说明。
- 支持配置模型 API 地址和密钥。
- 支持调用本地已安装的 AI 命令行工具，首批目标包括 Claude Code、Codex。
- 为其他模型接口和命令行工具保留适配能力；具体支持范围通过适配器及版本验证确定。

### 2.4 平台与视觉方向

- 使用 Swift 开发 macOS 客户端；界面优先采用 SwiftUI，必要时再评估 AppKit 补充。
- 遵循 Apple 设计规范，采用现代、温润的视觉风格，参考 Liquid Glass。
- 动画轻柔克制，圆角适度；代码、行号和增删差异的可读性优先。
- 正式界面以 `docs/design/workspace-reference.png` 和 `docs/design/history-reference.png` 的原始设计稿风格为基准，并保留后续已确认的交互修正。HTML 只作为操作流程参考，不作为正式视觉样式、配色值或控件实现依据。
- 支持切换应用主题，由主题系统统一管理强调色、背景层次、控件状态与材质。
- 支持独立切换代码配色主题，涵盖语法高亮、代码背景、行号、选中和差异／冲突颜色。
- 支持日间（浅色）、夜间（深色）和跟随系统模式；日夜模式、应用主题和代码主题分别保存。
- 支持浅色界面配深色代码、深色界面配浅色代码；代码主题可固定指定配色，也可设置浅深配色随应用的有效外观切换。
- 主题切换即时生效且重启后保留，不丢失当前仓库、文件选择、滚动位置、提交草稿或 AI 任务状态。

### 2.5 仓库入口、提交历史与图形

- 参考 IntelliJ IDEA 的布局特点，通过菜单打开或选择仓库。
- 左侧不常驻多个仓库的列表；窗口内容围绕当前打开的仓库组织。
- 能查看历史提交记录，并提供类似 Git Graph 的提交关系图。
- 同一项目关联 Git 与 SVN 的要求继续保留；历史界面需要明确当前查看的版本控制来源。

### 2.6 正式实现的模块约束

- 版本控制契约、具体适配器、业务编排、原生界面各自独立；模块边界见 [原生客户端架构](native-architecture.md)。
- 主题系统独立于版本控制和 AI；应用主题与代码主题分别定义颜色语义，不在页面内零散写死颜色。
- 应用组装入口注册适配器并注入依赖；业务和界面不通过 Git/SVN 字符串分支调用具体实现。

## 3. 已观察到的本地仓库布局

此前对用户指定的 EFB 目录进行了本地只读元数据检查：

| 布局 | 示例 | 设计影响 |
| --- | --- | --- |
| 同目录 Git 与 SVN 共存 | `EFB-ROOT-Service/ROOT-3.6.0.01-ZH`、`EFB-Adapter-Service/adapter-ZH` | 一个目录可以有两套独立版本控制绑定和比较基准 |
| 外层 SVN 包含内层 Git 工作目录 | `EFB-Adapter-Service/efbserver_maven` 及其部分 `branches`、`trunk` 子目录 | 需要识别嵌套范围，协调作用于相同文件的操作 |
| 单独使用 SVN 或 Git | `EFB-ROOT-Service/ROOT-3.6.5.01-EU`、`EFB-ROOT-Service/efb-old-server` | 按已识别能力提供操作 |

示例路径相对于 `/Users/zhangyiming/Documents/Code/EFB`。这些是兼容性样本，产品不应硬编码 EFB 目录或业务规则。

元数据检查可以证明工作目录及覆盖关系，不能证明 Git 与 SVN 远端内容一致，也不能确定 SVN 服务的 TLS 能力。

## 4. 建议的提交行为（待随界面设计确认）

### 4.1 提交准备

- 在同一提交入口展示目标、文件范围、比较基准及提交说明。
- 分别计算 Git 和 SVN 的待提交改动；两边的文件集合、状态和说明允许不同。
- Git 显示当前分支及暂存状态；SVN 显示对应路径和工作副本版本信息，不强制套用 Git 暂存区概念。
- 支持按目标预览最终内容。某个目标没有可提交改动时，明确显示无变更。
- 没有选择任何目标时，提交按钮不可执行。
- “Git 提交后推送”作为独立选项，建议初始默认关闭；这是建议值，尚未经用户确认。

### 4.2 执行与恢复

- 同一批次中，作用于共享文件或重叠工作副本的写操作顺序执行。
- 分别记录 SVN 提交、Git 提交及 Git 推送的结果。
- 双边提交不能假定为一个原子事务；一边成功、另一边失败时，保留已成功结果，并提供后续处理入口。
- 连接中断或超时导致结果不明时，先核实实际结果，再决定是否重试，避免重复提交。
- 双边执行顺序，以及一边失败后另一边是否继续，需要确定规则。
- Git 切换分支、拉取及 SVN 更新等修改文件的操作完成后，刷新受影响的全部版本控制绑定。
- 文件选择和提交范围应排除 `.git`、`.svn` 等管理数据；处理已有工作目录时不擅自改写忽略配置。

## 5. 建议的 AI 场景与执行方式

### 5.1 场景与连接分开配置

“场景”负责定义任务，“AI 连接”负责实际执行。同一个审查场景可以选择模型 API，也可以选择本机命令行工具。

| 配置对象 | 建议内容 |
| --- | --- |
| AI 场景 | 名称、用途、提示词、输入范围、输出要求、默认 AI 连接 |
| 模型 API 连接 | 名称、协议类型、服务地址、凭据引用、模型、超时等参数 |
| 命令行工具连接 | 工具类型、可执行文件位置、版本、可用状态及必要运行参数 |

接口协议不一致时由不同适配器处理，不能仅凭一个 API 地址保证兼容所有服务。命令行工具的具体调用和权限控制方式需要按实际版本验证。

### 5.2 场景执行建议

- 支持对待提交改动、选定历史提交或提交范围执行审查。
- 输入范围明确到版本控制目标、文件和比较基准；可以按需要提供相关文件上下文。
- Git、SVN 可以绑定不同的提交说明提示词，并分别编辑最终说明。
- 保存本次执行对应的改动快照标识。文件或提交范围变化后，提示原审查结果和提交说明可能已经过期。
- 审查与提交说明生成默认按只读任务运行；提交操作由客户端的明确提交动作触发。
- 展示执行进度、输出和错误，支持取消。
- 复用已安装 CLI 的登录能力，具体方法由工具适配器确定；应用凭据不进入普通日志或提示词。

## 6. 第一版验收场景草案

1. 导入已有目录，正确识别单 Git、单 SVN、同目录双版本控制及外层 SVN／内层 Git 布局。
2. 能从实际服务完成 Git 克隆和 SVN 检出，并明确显示目标目录和连接状态。
3. 能更新代码并查看历史、文件列表与差异；有本地改动或冲突时准确展示状态。
4. 提交目标分别选择 SVN、Git、两者时，操作范围与选择一致，各目标结果清楚可见。
5. 双边提交部分失败或结果不明时，能够定位当前状态，避免重复执行已完成步骤。
6. 创建并保存 AI 场景，修改提示词后能用于代码审查及提交说明生成。
7. 通过已配置的模型 API、Claude Code CLI、Codex CLI 分别执行支持的场景；未安装、未登录或执行失败时可定位原因。
8. AI 输出对应所选变更；变更再次修改后能够提示需要重新生成或复核。
9. 老 SVN 的连接兼容性通过真实服务验证；具体配置只作用于对应连接。
10. 能从菜单打开仓库，在当前仓库内切换工作区与提交历史；左侧不出现全局仓库列表。
11. Git 历史图能表达真实提交父子关系、分叉与合并，定位分支、标签和 HEAD；选择提交后可查看元数据、文件及差异。SVN 历史能够按修订号定位并查看路径变更。

12. 替换版本控制适配器或注入模拟适配器时，业务与界面无需修改；不支持的能力在调用前明确展示。
13. 应用主题、代码主题和日夜模式分别切换；浅色界面配深色代码及反向组合均可读，固定代码配色不被系统外观切换覆盖。
14. 跟随系统时响应外观变化；设置即时生效、重启后恢复，切换不清空工作区状态。
15. 原生工作区与历史视图对照原始设计稿验收；代码增删、冲突、选中和搜索高亮在各主题下能清楚区分。

## 9. 正式界面的布局基线与后续建议

- macOS 菜单“项目”提供打开仓库、最近打开、克隆／检出与关闭；多仓库可通过不同窗口处理，窗口行为细节待定。
- 工作区：左侧当前仓库的文件／变更列表，中间差异阅读，提交与 AI 面板按需打开。
- 历史：底部停靠并可放大为主视图；左侧分支／标签，中间提交图与列表，选择提交后联动文件、元数据与差异。
- 历史筛选建议支持提交说明、作者、日期、分支及文件路径；支持复制版本号、单文件历史和选择版本比较。
- Git Graph 的连线来自提交父子关系。SVN 先提供修订历史；复制来源和合并关系需要相应元数据，不能按时间顺序臆造为 Git 式拓扑。
- Git 与 SVN 历史分别切换。若以后提供跨系统对应关系，需要可核验的映射依据，不能仅凭时间或相同提交说明自动认定对应。
- 底部操作日志可收起；文件差异可切换并排／统一模式，并可放大阅读。面板尺寸可调整并记住，历史选择与滚动位置应在切换视图后保留。
- 玻璃材质集中在导航及操作区域，代码与提交列表保持稳定对比度；响应系统减少动态效果与降低透明度设置。

## 10. HTML 交互原型范围

`prototype` 是用于确认日常操作流程的高保真 HTML 交互原型，不是正式客户端实现。

- 开发运行命令：`npm run dev -- --host 127.0.0.1 --port 4173`；`npm run export:html` 可生成单文件 `rephub.html`。
- 支持从“项目”菜单打开示例仓库，以及模拟 Git／SVN 的克隆或检出；左侧仅展示当前仓库的文件和变更。
- 支持工作区差异阅读、并排／统一差异切换、Git 提交图、SVN 修订历史及历史提交差异查看。
- 支持 AI 场景与连接配置，并以预设结果体验代码审查和提交说明生成；API 密钥只在设置弹窗内存中存在，绝不持久化。场景和非密钥连接配置可保存于当前浏览器的 `localStorage`。
- 支持勾选 Git、SVN 或两者作为提交目标；每个目标独立记录模拟结果，部分失败时只能重试失败目标。
- “帮助”可恢复当前仓库的 mock 演示数据，方便重复体验流程。
- 原型不读取真实仓库、不执行 Git／SVN／CLI 命令、不联网，也不产生真实提交、更新、克隆或检出操作。
- 正式 Swift 客户端、实际 AI API／CLI 调用、真实 Git／SVN 操作和旧版 SVN TLS 兼容性验证，均留待后续实现与真实服务验证。

### 10.1 本地文件夹检测与版本控制接入

- 打开本地文件夹时，先检测其是否已受 Git、SVN 或两者管理；已识别时直接打开并展示对应绑定，不重复初始化。
- 未受版本控制的目录应单独展示为“未受管理”，由用户单选创建 Git 或接入 SVN，初始化只能选择一种方式；用户确认后才开始相应操作，成功后打开该工作区，取消则不写入目录。
- 检测失败不等同于“未受管理”。例如权限、损坏元数据或工具不可用导致的失败，应说明原因并只提供重试或退出，不能允许误初始化覆盖已有元数据。
- 正式客户端的 Git 检测需要识别 `.git` 目录和 `gitdir` 文件，并向上识别父级工作区与嵌套范围；SVN 检测需要识别 `.svn` 工作副本。检测结果须关联实际根目录，避免对同一工作副本重复初始化。
- Git 初始化创建的是没有提交历史的仓库；目录中的文件应作为待首次提交内容展示，不能把初始化本身表述为已有首个提交。[Git `git-init` 文档](https://git-scm.com/docs/git-init)
- SVN 没有可对现有目录直接等价于 Git 初始化的本地流程。接入已有 SVN 服务时，用户必须提供目标 URL，并选择导入现有目录或检出工作副本；`svn import` 会把目录副本递归提交到 URL，原目录随后仍不是工作副本，通常还需检出新的工作副本。[SVN `import` 文档](https://www.visualsvn.com/support/svnbook/ref/svn/c/import/)
- 因此，SVN 导入会产生首个修订；导入／检出必须保护原目录。目标冲突、传输中断和双目标部分失败时，需要保留已完成结果，提供明确恢复路径，不能假设存在 `svn init`。
- 当前 HTML 原型只模拟目录选择、检测、初始化确认与打开结果，不读取目录、不执行命令、不访问 SVN 服务。其他版本控制系统仅保留适配器扩展入口，尚未实现。
