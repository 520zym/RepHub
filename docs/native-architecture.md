# RepHub 原生客户端架构与视觉约束

状态：2026-10-11。已建立 Swift Package 原生工程、读取工作台与已有仓库更新；本文件同时保留完整目标约束，未列入下方“当前实现”的内容仍是后续计划。

当前实现：独立契约模块、Git / SVN 适配器、目录双绑定识别、状态 / 差异 / 最近 150 条历史读取、Git 父子图、主题系统及原生设置。工具通过参数数组运行，支持超时和取消。已有仓库支持 Git fetch / 快进更新及 SVN update，单选目标并刷新全部绑定。SVN 在默认连接出现协议握手兼容错误时自动尝试旧 TLS，成功后按 HTTPS 主机与端口短期缓存，无需界面配置；写入前只读探测，更新命令仅执行一次。初始化类型只能指定一个 provider，但执行尚未接入；提交、推送、AI、历史分页、关联不同目录、后台监控和完整语法高亮尚未实现。SVN 使用本机已有工具与认证配置；不降低全局 TLS 或绕过证书错误。

## 1. 版本控制独立分层

运行时：原生界面 → 工作区业务 → 版本控制契约 → Git／SVN／其他适配器 → 工具执行基础设施。

编译依赖与运行时调用区分：适配器依赖契约，契约不依赖任何具体适配器；应用入口负责注册实现和注入依赖。

| 建议模块 | 职责与依赖边界 |
| --- | --- |
| VersionControlCore | 独立 Swift 模块，定义领域模型、能力接口、错误和操作结果；不依赖 SwiftUI、进程命令或具体工具 |
| GitAdapter / SVNAdapter | 实现契约，构造命令并解析输出，保留工具专属语义；依赖契约和基础设施 |
| RepositoryApplication | 仓库识别、操作计划、共享路径协调、结果恢复及刷新；只依赖工具契约 |
| DesignSystem | 应用主题、代码主题、外观解析和原生组件样式；不依赖仓库工具或 AI |
| RepHubUI | 工作区、历史、设置与 AI 界面；调用业务服务，不运行 CLI |
| RepHubApp | 启动、窗口、设置持久化和依赖组装；仅组装入口引用具体适配器 |

第一轮使用静态适配器注册表，不要求动态插件加载。扩展新工具时不修改现有业务和视图中的工具类型分支。

### 契约与能力

- `VersionControlProvider` 提供类型标识、显示名、可用性与目录检测入口。注册表可返回多个匹配绑定。
- `RepositoryHistoryProvider` 独立提供单文件历史、历史路径差异及同步状态；`FileHistoryEntry` 保留适配器追溯所需的路径和锚点。业务层校验相对路径并单独保留同步读取错误，UI 不解析命令输出。Git 保留分支上游语义，SVN 保留工作副本 BASE 与混合修订语义。
- `RepositoryOperationProvider` 单独定义异步写操作入口，使用 `RepositoryOperationKind`、阶段进度与 `RepositoryOperationResult`；界面不导入 Git / SVN 模块。`RepositoryService` 负责同实例操作互斥、目标复核、取消后脱离取消上下文刷新所有绑定。
- `RepositoryBinding` 包含实际工作副本根目录、在工作区内的覆盖范围、远端信息和可用能力。一个工作区允许多个绑定；嵌套和共管不能只用一个仓库类型枚举表示。
- 检测结果区分已识别、确认未管理、工具缺失、权限不足、元数据损坏与未知错误；检测失败不能降级为“未管理”。
- 按状态、差异、分页历史、工作副本获取／初始化、更新和提交拆分能力。暂存、推送、分支和提交拓扑为可选能力；根据绑定及工具版本判定是否可用。
- 修订标识、比较基准、路径状态、文本／二进制差异、提交父子关系使用结构化模型。SVN 不伪造 Git 暂存区或 Git Graph。
- 命令参数、输出解析、退出码、工具路径和 TLS 兼容配置封装在适配器／基础设施；UI 不读取 stdout 判断成功。旧 TLS 自动回退只作用于对应 HTTPS 端点的只读命令，缓存不持久化；超时、取消、认证及证书错误不触发回退。未来写操作不能直接套用只读命令的重试逻辑。
- 操作提供异步进度、取消、超时和结构化结果。成功、失败、取消、结果未知分别表达；网络超时后先核实实际结果再重试。
- 同目录及重叠目录的写操作由业务层协调，完成后刷新所有受影响绑定；多目标提交分别保存结果，不重复执行已成功目标。

### 初始化与提交不能共用多选状态

`InitializeRequest` 只接受一个 `providerID`，对应 Git 或 SVN 单选；`CommitPlan` 可包含多个已存在的绑定。已有双管控目录继续识别。SVN 接入按真实导入／检出流程定义，不实现虚构的本地 `svn init`。

## 2. 三项独立的外观设置

| 设置 | 负责内容 | 建议默认行为 |
| --- | --- | --- |
| 应用主题 `AppThemeID` | 强调色、导航／面板层次、边界、控件状态、图表配色、材质 | 首版至少两套完整主题；默认按原设计稿的温润风格 |
| 日夜模式 `AppearancePreference` | 跟随系统、日间浅色、夜间深色 | 默认跟随系统；手动指定后不受系统切换覆盖 |
| 代码配色 `CodeThemeSelection` | 代码背景／前景、语法、行号、选中、搜索、增删和冲突 | 可固定配色，也可指定随有效外观切换的浅／深配色组合 |

设置入口建议为原生设置中的“外观”和“代码配色”。顶部 AI 审查右侧不恢复重复设置齿轮。

解析顺序：

1. 按日夜模式与系统外观得到有效的浅色或深色。
2. 取所选应用主题的对应变体。
3. 固定代码配色直接使用；自动代码配色按有效外观选择其浅／深版本。
4. 更新样式并独立保存偏好，不重建仓库会话或清空当前任务。

浅色应用配深色代码、深色应用配浅色代码都是有效组合。切换应用主题不改写代码主题选择；系统切换仅影响设为跟随的项目。

### 实现约束

- 页面使用语义样式，不零散写死颜色。应用主题和代码主题分别定义，强调色不能覆盖增删、语法和状态颜色。
- 代码主题完整覆盖普通文本、背景、关键字、字符串、数字、注释、类型、行号、选中、光标、当前行、搜索、增删和冲突；叠加选中和搜索后仍能辨认差异。
- 代码／差异区域有稳定底色，新增与删除同时保留符号、行号及状态文字，不只依赖颜色。
- 应用主题均提供浅／深变体，深色按原设计的层次配色，不简单反色。菜单、弹窗、提示和 Git Graph 一并适配。
- 即时切换并在重启后恢复；保留仓库、文件选择、历史筛选、滚动位置、提交草稿和进行中的 AI 任务。
- 尊重减少动态效果和降低透明度设置；具体 Liquid Glass API 与系统版本回退在原生工程建立时验证。

- [工作区原始设计稿](design/workspace-reference.png)
- [历史原始设计稿](design/history-reference.png)

采用原稿的浅净、温润、轻玻璃导航和清晰代码区域，保留适度圆角与柔和交互。使用原生菜单、工具栏、分栏、表格和设置窗口；内容区不仿画系统菜单栏或窗口红黄绿按钮。

HTML 只用于核对操作流程，不复制其 CSS 配色、尺寸、阴影或网页组件作为正式视觉标准，也不将其嵌入原生窗口作为主界面。

原稿中的生成文字、日期和示例拓扑不是产品数据。后续明确要求优先：初始化单选、移除顶部重复设置、菜单切换仓库、侧栏仅显示当前仓库。未覆盖的深色方案应按上述风格制作原生预览并检查。

## 4. 首轮交付与验收

- 建立独立模块、原生窗口和可注入工具接口，完成 Git/SVN 识别及读取的纵向流程；模拟适配器只用于预览与隔离验证，真实能力通过实际目录验证。
- 在原生骨架阶段接入主题、代码配色和日夜模式，避免后续逐页修改固定颜色。
- 替换适配器时界面与业务不导入具体实现；不支持的能力有明确状态。
- 每个应用主题检查浅／深／跟随系统模式，另检查固定浅代码、固定深代码和自动代码配色；系统切换不覆盖固定设置。
- 工作区和历史对照原始设计稿，检查差异、选中、搜索、冲突、语法高亮、Git Graph、弹窗及辅助功能偏好。
- 切换后继续操作并重启，确认偏好保留，切换不清空工作区和任务状态。
